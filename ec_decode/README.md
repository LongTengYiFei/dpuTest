# DOCA EC correctness and CPU comparison

`ec_compare` validates the five representative 4+2 loss classes and compares
repair latency with Jerasure:

1. one data chunk (`D1`)
2. one parity chunk (`P0`)
3. two data chunks (`D1,D2`)
4. two parity chunks (`P0,P1`)
5. one data and one parity chunk (`D1,P0`)

Build and run:

```bash
make ec_compare
./ec_compare --pci b1:00.0 --block-size 1MB --iterations 100
```

Options:

```text
--pci <BDF>              DOCA device (default: b1:00.0)
--block-size <size>      Chunk size, aligned to 64 bytes (default: 1MB)
--iterations <count>     Measured iterations per case (default: 100)
--warmups <count>        Warm-up iterations per case (default: 5)
--matrix <type>          cauchy or vandermonde (default: cauchy)
```

The two implementations generate and validate against their own parity because
a matrix name does not guarantee byte-for-byte compatibility between libraries.
DOCA uses `recover` for missing original data. Missing parity is regenerated
with `create`; the mixed case therefore measures `recover + create`. Jerasure's
single decode call reconstructs both data and coding blocks.

The recover input always contains exactly `K` chunks in ascending codeword
order. On DOCA 3.0, a parity hole before the Kth selected chunk must be included
in the recovery-matrix index list so the library can identify a later parity
chunk. For example, loss of `D1+P0` uses `D0,D2,D3,P1` and indices `[1,4]`.
Only the recovered data prefix is trusted; parity is regenerated by `create`.

The reported time excludes setup, matrix generation, initial encoding, and the
CPU buffer reset performed before each measured decode. DOCA mixed repair does
include the host copy that connects the recover output to the create input.
The `CPU/DOCA` column is a latency ratio, so values above 1.0 mean DOCA has
lower latency.
